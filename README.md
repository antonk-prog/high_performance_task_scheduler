# Task scheduler — C++17

Thread pool с локальными **Chase–Lev deque**, кражей задач через CAS и атомарными
входящими очередями. В коде планировщика нет `mutex`, `condition_variable` и spinlock.
Сборка — CMake, сторонних зависимостей нет.

## Сборка и запуск

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure
./build/scheduler_example
```

Нужны CMake 3.16+, C++17 и платформа с lock-free атомиками для указателей,
64-битных индексов, `size_t` и `bool`. Это проверяется через `static_assert`.

## Использование

```cpp
#include "task_scheduler/thread_pool.hpp"

#include <iostream>
#include <memory>

int main() {
    task_scheduler::ThreadPool pool(4, 1024); // workers, размер локального кольца
    int result = 0;

    pool.submit([value = std::make_unique<int>(42), &result] {
        result = *value;
    });

    pool.wait_idle();
    std::cout << result << '\n';
}
```

`submit()` принимает callable без аргументов, включая move-only лямбды. Несколько
внешних потоков могут вызывать его одновременно. Работающая задача тоже может
вызывать `submit()` для создания дочерних задач. Возвращаемое значение callable
игнорируется; результаты можно записывать в принадлежащие вызывающему объекты.

- `ThreadPool()` по умолчанию использует `hardware_concurrency()`, минимум 1 worker.
- `ThreadPool(workers, capacity)` задаёт число потоков и размер каждого кольца.
  `workers > 0`, `capacity >= 2` и является степенью двойки.
- `wait_idle()` ждёт завершения всех задач, включая дочерние и уничтожение их
  callable-объектов. После него результаты задач видны вызывающему потоку.
- `thread_count()` возвращает число worker-ов.
- `failed_tasks()` возвращает число задач, выбросивших исключение. Исключение
  перехватывается, worker продолжает работать. Само исключение не сохраняется.
- Деструктор завершает все принятые задачи и присоединяет потоки.

Ошибка выделения памяти или конструирования callable выходит из `submit()`:
в этом случае задача не принята и счётчик незавершённых задач не увеличивается.

## Как устроена работа

У каждого worker-а есть:

1. **Локальная bounded Chase–Lev deque.** Владелец добавляет и снимает задачи с
   `bottom` (LIFO). Другие worker-ы крадут с `top` (FIFO) через CAS. За последнюю
   задачу владелец тоже борется через CAS.
2. **MPSC inbox.** Внешние отправители добавляют задачи через CAS в атомарный
   односвязный список. Worker забирает весь список через `exchange`, разворачивает
   его и порциями до 32 задач переносит в свою deque.

```text
external producers ── round-robin ──> worker inbox ──> local deque
                                                         ↑   ↓
                                              submit / pop   steal (CAS)
                                                         ↑   ↓
                                                     workers
```

Задача, созданная внутри этого пула, сразу попадает в deque текущего worker-а.
При заполненном кольце она попадает в его inbox. Вызов из worker-а другого пула
считается внешней отправкой.

Размер кольца фиксирован, но это **не лимит общего количества задач**: переполнение
уходит во входящий список. Поэтому не нужны рост кольца, hazard pointers или
отложенное освобождение старых буферов. Слоты кольца атомарные: задержавшийся вор
может прочитать уже переиспользуемый слот, но разыменовывает указатель только после
успешного CAS. Задачу удаляет тот поток, который получил право её выполнить.

В inbox отправитель не разыменовывает старую голову списка: только сохраняет её
значение в `next` своей задачи и сравнивает через CAS. После успешного `exchange`
отсоединённым списком владеет только потребитель.

`top` и `bottom` разнесены по 64-байтным cache line. Acquire/release публикуют
задачи; `seq_cst` fence и CAS разрешают гонку владельца с ворами. Комментарии к
этим местам находятся непосредственно в коде.

## Правила использования

- Перед `wait_idle()` завершите внешних отправителей, если нужно дождаться всего
  отправленного ими набора. При продолжающемся `submit()` ожидание может увидеть
  временный ноль до следующей отправки.
- Перед уничтожением пула завершите внешние обращения к нему. Уже работающим
  задачам разрешено добавлять дочерние задачи во время завершения пула.
- `wait_idle()` из задачи **этого же** пула выбрасывает `logic_error`: задача сама
  входит в счётчик незавершённых. Уничтожение пула из собственной задачи вызывает
  `std::terminate()`.
- Задачи должны быть короткими и не блокировать worker в ожидании других задач
  того же пула. Иначе можно занять все worker-ы ожиданием. Чужой inbox нельзя
  красть напрямую — его задачи становятся доступны ворам после переноса в deque.
- Захваченные по ссылке объекты должны жить до завершения задач. Общие изменяемые
  данные внутри задач требуют собственной синхронизации.
- Порядок выполнения задач не гарантируется.

## Компромиссы производительности

Простой путь отправки делает одно выделение памяти на задачу. Очереди и счётчики
используют только lock-free атомики, но аллокатор, создание потоков и пользовательский
код могут использовать внутренние блокировки. Поэтому весь `submit()` не заявляется
формально lock-free.

Для завершения используется общий атомарный счётчик. При очень мелких задачах
его cache line, выделение памяти и round-robin счётчик отправителей могут стать
узкими местами. Реализация оставляет эти механизмы явными и простыми.

Пустые worker-ы опрашивают очереди с `_mm_pause()` на x86 и периодическим
`std::this_thread::yield()`. Парковки через ОС нет: пул расходует CPU и в простое.
Обход воров — линейный по числу worker-ов со сдвигающимся началом.

Индексы Chase–Lev — знаковые 64-битные; переполнение не поддерживается.
За время жизни одной deque должно быть менее `INT64_MAX` успешных добавлений.

## Тесты и sanitizers

Тесты проверяют пустую и заполненную deque, переиспользование кольца, гонку
владельца с несколькими ворами, ровно одно выполнение каждой задачи, несколько
отправителей, видимость результатов после ожидания, дочерние задачи, переполнение,
move-only captures, исключения, отправку между пулами и drain в деструкторе.
Проверки работают и в Release, независимо от `NDEBUG`. CTest ограничивает время
тестового процесса 120 секундами.

```bash
cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug -DTASK_SCHEDULER_ASAN_UBSAN=ON
cmake --build build-asan -j
ASAN_OPTIONS=detect_leaks=1 UBSAN_OPTIONS=halt_on_error=1 ctest --test-dir build-asan --output-on-failure

cmake -S . -B build-tsan -DCMAKE_BUILD_TYPE=Debug -DTASK_SCHEDULER_TSAN=ON
cmake --build build-tsan -j
TSAN_OPTIONS=halt_on_error=1 ctest --test-dir build-tsan --output-on-failure
```

ASan/UBSan и TSan собираются отдельно. GCC TSan предупреждает, что не моделирует
`atomic_thread_fence`: успешный запуск TSan дополняет стресс-тесты, но не доказывает
корректность протокола Chase–Lev. В тестах нет инъекции отказов создания потоков
или аллокатора; проверки на weak-memory архитектурах отдельно не проводились.

## Benchmark

```bash
# workers tasks producers work
./build/scheduler_benchmark 4 200000 4 32
```

Три сценария: один внешний отправитель, несколько внешних отправителей,
генерация дочерних задач из worker-а с work stealing. `work` задаёт количество
шагов вычисления в каждой задаче. Выводятся полное время отправки и выполнения,
пропускная способность и checksum; checksum всех сценариев должен совпадать.
Время создания внешних producer-потоков включено, время создания пула — нет.
Результаты зависят от CPU, нагрузки, размера задач и аллокатора.

## Файлы

Весь C++-код, включая заголовки, находится в `src/`:

```text
CMakeLists.txt
src/
  thread_pool.cpp
  task_scheduler/
    thread_pool.hpp
    detail/
      chase_lev_deque.hpp
      inbox.hpp
      task.hpp
      spin_wait.hpp
  examples/basic.cpp
  tests/scheduler_tests.cpp

```

Для подключения в другом CMake-проекте:

```cmake
add_subdirectory(path/to/high_performance_task_scheduler)
target_link_libraries(your_target PRIVATE task_scheduler)
```
