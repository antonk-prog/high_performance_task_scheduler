### Опорные черновики владельца и их судьба

Владелец предоставил три черновика (по мотивам книги Э. Уильямса «C++ Concurrency in Action»):

1. **`function_wrapper`** — обёртка произвольного вызываемого объекта через `unique_ptr` на базовый класс с виртуальной функцией вызова. **Берётся как основа** (решение D3): она решает реальную проблему — `std::function` требует, чтобы объект можно было копировать, а `std::packaged_task` копировать нельзя (результат «потребляется» один раз). Правки минимальны и перечислены в D3.
2. **Цикл воркера с каскадом** «своя дека → общая очередь → кража по кругу». **Перерабатывается**: порядок каскада сохранён по духу, но «общая очередь» заменена inbox'ами, старт кражи — случайный, `yield()` — только средней фазой трёхфазного ожидания.
3. **Lock-free стек со схемой отложенного удаления** (`threads_in_pop` + список `to_be_deleted`). **Отклонён** по решению владельца — заменён на hazard pointers (D6). Причины: (а) схема удаляет память только в моменты, когда в `pop` нет других потоков — при непрерывном трафике задачи это почти никогда, список неосвобождённых узлов растёт неограниченно; (б) односвязный список принципиально даёт один конец, а воркеру нужна двусторонняя дека — для неё Chase-Lev (D4).

## Goals / Non-Goals

**Goals:**
- Work-stealing пул с «горячим путём» владельца без блокировок: fork-join подзадачи кладутся и забираются без конкуренции (Chase-Lev).
- Приём внешних задач без глобальной мьютекс-очереди: inbox случайного воркера (очередь Майкла-Скотта + hazard pointers).
- API `submit(F) → std::future<T>` для любых вызываемых объектов; исключения задач доставляются в future, пул не падает.
- Два режима остановки + безопасный деструктор (graceful + join).
- Бенчмарки против наивного мьютекс-пула, запускаемые из CMake, с проверкой корректности внутри сценариев.
- Код портфолио-качества: осмысленные `memory_order` с обоснованием у каждой операции, RAII, минимум «умного» кода.

**Non-Goals:**
- Отмена выполняющихся задач, приоритеты, continuation-цепочки (`then`) — возможные будущие версии.
- Тестовый фреймворк, автотесты, CI — отложено владельцем.
- Динамическое изменение числа воркеров, привязка потоков к ядрам (CPU pinning), NUMA-осведомлённость.
- Оптимизация любой ценой: где честность и ясность конфликтуют со скоростью на проценты — выбираем ясность (пример: seq_cst CAS кражи в D4).

## Словарь терминов

| Термин | Значение простыми словами |
|---|---|
| **Атомарная операция** | Операция над переменной, которую процессор выполняет как единое неделимое целое; другие потоки никогда не видят её «наполовину выполненной». |
| **CAS (compare-and-swap)** | Атомарная операция: «если значение равно тому, что я прочитал раньше — замени на новое и ответь успехом; иначе ответь неудачей». Неудача означает: кто-то опередил — попытку повторяют. |
| **memory_order** | Указание компилятору и процессору, насколько строго упорядочивать операции вокруг атомарной. `relaxed` — «только атомарность, без порядка»; `acquire`/`release` — «пары запись→чтение, устанавливающие видимость данных»; `seq_cst` — «самый строгий общий порядок всех потоков». |
| **Lock-free** | Без мьютексов; дополнительно гарантируется: если система в целом продвигается, то хотя бы один поток завершает операцию (зависший поток не останавливает всех). |
| **Дека (deque)** | Двусторонняя очередь: элементы кладутся и забираются с обоих концов. |
| **Кольцевой буфер** | Массив, используемый «по кругу»: за последним индексом следует первый (индекс маскируется: `i & (ёмкость−1)`, ёмкость — степень двойки). |
| **Use-after-free** | Обращение к памяти после её освобождения — классическая катастрофа lock-free структур на указателях. |
| **ABA-проблема** | Поток читает значение A, отвлекается; meanwhile значение менялось на B и обратно на A; поток ошибочно считает, что «ничего не менялось». В проекте снимается 64-битными монотонными счётчиками (D4) и схемой Майкла-Скотта (D5). |
| **Future / promise** | Пара «квитанция / обещание»: задача через promise публикует результат (или исключение), вызвавший поток забирает его через future. `std::packaged_task` — стандартный связующий адаптер. |
| **Fork-join** | Схема «разделяй-и-властвуй» в параллельном виде: задача порождает подзадачи (fork) и дожидается их результатов (join). |
| **Потерянное пробуждение** | Ошибка паркинга: сигнал «есть работа» пришёл до засыпания, а проверка была раньше сигнала — поток спит вечно при лежащей работе. |
| **Громкое стадо (thundering herd)** | Ошибка пробуждения: будят всех спящих, работу получает один, остальные напрасно проснулись и легли обратно. |

## Ликбез: как читать `memory_order` в этом документе

Правило пары: запись `X.store(v, release)` в потоке A и чтение `X.load(acquire)` в потоке B, которое увидело записанное значение, образуют синхронизацию — **всё**, что поток A делал до store, поток B видит после load. Это основной инструмент: публикуем данные обычной записью, а «флаг готовности» — атомарным store/release; читатель делает load/acquire флага и гарантированно видит данные.

- `relaxed` — «сделай атомарно, порядок не важен»: для счётчиков и данных, никому не видимых без отдельного флага.
- `acquire` — на чтении «приёмника»: не переупорядочивай последующие чтения/записи раньше него.
- `release` — на записи «передатчика»: не переупорядочивай предшествующие чтения/записи позже него.
- `seq_cst` — самый сильный: единый глобальный порядок всех seq_cst-операций. Там, где в классических алгоритмах важны взаимные порядки двух разных атомарных переменных (как `top` и `bottom` в Chase-Lev), — оставляем seq_cst, потому что acquire/release пар недостаточно.

## Decisions

### D1. Общая архитектура: деки Chase-Lev + inbox-очереди

```
                ВНЕШНИЕ ПОТОКИ (main и др.)
                        │ submit(task)
                        ▼
         выбирается СЛУЧАЙНЫЙ воркер k
                        │
                        ▼
        ┌───────────────────────────────────┐
        │  inbox #k                          │
        │  очередь Майкла-Скотта (lock-free) │   ← много производителей
        │  память: hazard pointers           │     (любые внешние потоки),
        └────────────────┬──────────────────┘     один потребитель (владелец)
                         │ владелец забирает при опустошении деки
                         ▼
┌────────────────────────────────────────────────────────┐
│ WORKER k (поток-воркер)                                │
│                                                        │
│   ┌─ поиск следующей задачи, по приоритету: ────────┐  │
│   │ 1. pop из СВОЕЙ деки (Chase-Lev, конец bottom)  │  │ ← fork-join: submit
│   │ 2. pop из СВОЕГО inbox                           │  │   изнутри задачи
│   │ 3. steal из деки соседа (конец top,              │  │   кладёт прямо сюда
│   │    случайный старт, обход по кругу)              │  │
│   └──────────────────────────────────────────────────┘  │
│                                                        │
│   всё пусто → spin (~32) → yield (~8) → park (condvar) │
└────────────────────────────────────────────────────────┘
```

Почему так:

- **Дека — только для владельческих кладений.** Протокол Chase-Lev не позволяет чужому потоку класть в деку (атомарной «вставки сверху» не существует). Следствие: внешним задачам нужен отдельный вход — inbox.
- **Inbox, а не глобальная очередь** (решение владельца: «клади случайному воркеру»): у глобальной очереди две беды — она общий мьютекс-подобный узкий место (даже lock-free — одна точка конкуренции кэш-линий) и она нужна всем воркерам постоянно. Inbox'и распределяют внешнюю нагрузку по N независимым очередям; воркер проверяет только свой.
- **Hazard pointers в inbox обязательны, а не роскошь**: производители (внешние потоки) разыменовывают `tail` и `tail->next` (схема Майкла-Скотта, D5) в тот момент, когда потребитель извлекает и ретирит головные узлы. Без защиты — use-after-free. Схема из черновика владельца (`threads_in_pop`) защищала бы только потребителя; производители остались бы незащищены.

Отклонённые альтернативы:

| Альтернатива | Почему отклонена |
|---|---|
| Мьютекс-деки (как в книге Уильямса, гл. 9) | Проще, но исчезает вся lock-free-часть проекта — главная цель (портфолио). |
| Глобальная очередь (мьютекс или lock-free) для внешних задач | Общая точка конкуренции; противоречит решению владельца «случайный воркер». |
| Класть внешнюю задачу прямо в деку воркера | Невозможно по протоколу Chase-Lev (см. выше). |
| Стек из черновика владельца как дека | Односвязный список = один конец; дека требует двух. |

### D3. `function_wrapper` — по черновику владельца, с правками

Назначение (из черновика, сохраняется): хранить любой вызываемый объект за стёртым типом. Механика: иерархия `impl_base` (виртуальный вызов) / `impl_type<F>` (хранит объект), владение через `std::unique_ptr`, копирование запрещено, перемещение разрешено.

Правки относительно черновика (мелкие, смысл не меняют):

| Правка | Зачем |
|---|---|
| `operator()` вместо метода `call()` | Идиоматично: обёртка вызывается как функция. |
| Конструктор и присваивание по умолчанию (пустая обёртка) | Нужен деке/очереди для неинициализированных слотов; вызов пустой обёртки — `assert`/`std::terminate`. |
| Перемещающие операции — `noexcept` | Обязательное требование к элементу контейнера с перегрузкой (иначе `std::vector` при росте падает в копирование). |
| `explicit` у шаблонного конструктора | Запрет неявных конверсий «лямбда → обёртка» в неожиданных местах. |

*Эскиз интерфейса (не реализация — реализация в задаче 2.1):* конструктор из `F&&`, перемещение, `operator()`, удалённое копирование, «пуста?».

### D4. Chase-Lev дека: состояние, операции, модель памяти

#### Состояние

- `std::atomic<int64_t> top` — индекс «старого» конца (за него воюют воры).
- `std::atomic<int64_t> bottom` — индекс «свежего» конца (только владелец).
- `std::atomic<Buffer*> buf` — указатель на кольцевой буфер; буфер хранит массив слотов и ёмкость (степень двойки). Индекс слота: `i & (ёмкость−1)`.
- Счётчики 64-битные и **монотонно растут вечно** (не заворачиваются по ёмкости — заворачивается только индекс в массиве). Переполнение int64 на практике недостижимо; тем самым снята ABA на счётчиках: «увиденное значение изменилось и вернулось» невозможно, значения только растут.

Ключевая асимметрия производительности: `push` владельца и обычный `pop` владельца не содержат CAS вообще — одна-две атомарные записи. CAS появляется только у воров и в редком граничном случае pop'а.

#### `push` (только владелец)

1. Прочитать `bottom` (relaxed — некому с ним соревноваться, мы единственный писатель этого конца) и `top` (acquire — увидеть актуальные чужие записи).
2. Если буфер полон (`bottom − top == ёмкость`) — выполнить рост (см. ниже).
3. Записать задачу в слот `bottom & mask` — обычная (relaxed) запись: до публикации через `bottom` её никто не увидит.
4. `bottom.store(b + 1, release)` — **публикация**: любой вор, чей acquire-CAS по `top` отрежет этот слот, обязан увидеть задачу целиком (правило пары из ликбеса).

#### `pop` (только владелец)

1. `bottom.load(acquire)`; уменьшить на единицу: `b = bottom − 1`.
2. Если `b < top` — дека пуста (гонка с вором возможна, см. шаг 4): `bottom.store(top, release)` — выровнять свой конец с чужим; вернуть «пусто».
3. Обычный случай (`b > top`): прочитать слот `b & mask`, задача наша без всякого CAS (воры не могут тронуть этот слот, пока `top < b`)... крайний случай `b == top` — **последняя задача**, на неё одновременно может претендовать вор: `bottom.store(b, relaxed)`; CAS `top: t → t + 1` (**seq_cst**, успех — задача наша, неудача — её украл вор, вернуть «пусто»).
4. Если задача получена — вернуть её.

Почему CAS именно seq_cst: здесь сталкиваются порядки двух разных атомарных переменных (`top` и `bottom`), и доказанная корректность Chase-Lev (адаптация Лева–Лоуро–Мура для слабых моделей памяти) опирается на общий порядок. Это осознанное «неоптимизируемое» место.

#### `steal` (любой поток)

1. `top.load(acquire)` — `t`.
2. Если `t >= bottom.load(acquire)` — пусто, вернуть «пусто».
3. Защитить буфер: опубликовать `buf.load()` в hazard-слоте (владелец мог заменить буфер ростом; слот гарантирует, что массив не освободится под нашими руками — см. «Рост»).
4. Перечитать задачу из слота `t & mask` **до** CAS (после успешного CAS слот может быть перезаписан владельцем).
5. CAS `top: t → t + 1` (**seq_cst**): успех — задача наша (и всё, что владелец записал до своего release-store `bottom`, нам видно); неудача — кто-то опередил (вор или владелец в крайнем случае pop), вернуть «пусто» (повтор — на уровне вызывающего цикла, steal однопопытен).
6. Снять hazard-публикацию буфера.

#### Рост буфера (только владелец)

Триггер: `push` обнаружил `bottom − top == ёмкость`.

1. Выделить новый буфер вдвое больше; перенести все `ёмкость` задач со старых позиций `top..bottom` (позиции вычисляются заново в новом масштабе маски).
2. `buf.store(new_buf, release)` — публикация; воры со следующего перечитывания работают с новым массивом.
3. Старый буфер — **не удалять немедленно**: активный вор может держать его через hazard-слот (шаг 3 steal). Старый буфер отправляется в retire-механизм (D6) и освобождается, когда ни один слот на него не указывает.

Почему рост — только владелец: только владелец знает консистентную пару (`top`, `bottom`) для переноса; воры в момент роста либо успели украсть (CAS по `top` до публикации), либо будут работать с новым буфером.

#### Инварианты корректности (для ревью, задача 3.5)

- Каждый слот диапазона `[top, bottom)` содержит ровно одну неприсвоенную задачу; слоты вне диапазона — мусор, читать их нельзя.
- Задача покидает деку ровно один раз: либо владелец выиграл CAS (pop, крайний случай), либо вор (steal), либо владелец забрал её в обычном порядке без CAS.
- Видимость: слот читается вором только после успешного seq_cst-CAS `top`, который синхронизирован с release-store `bottom` владельца, сделанным при укладке этой задачи.

### D5. Inbox: очередь Майкла-Скотта с фиктивным узлом

Узел: `{ function_wrapper task; std::atomic<node*> next; }`. Очередь: `std::atomic<node*> head, tail`. Инвариант Майкла-Скотта: `head` всегда указывает на фиктивный узел без данных; первый реальный элемент — `head->next`; `head == tail` означает «пусто».

#### `push` (любое число внешних потоков)

1. Создать узел с задачей (`next = nullptr`).
2. Защитить `tail` через hazard-слот: прочитать `tail` → опубликовать → перечитать `tail` (протокол D6). Если изменился — повторить.
3. `next = tail->next.load(acquire)`.
4. Если `next == nullptr` (хвост действительно последний): CAS `tail->next: nullptr → новый узел` (release — публикация узла). Успех — перейти к 5; неудача — другой производитель успел первым: перечитать `tail`, повторить с шага 2.
5. Продвинуть `tail` CAS'ом `tail: старый → новый узел` (допустимы и неудачи: хвост продвинет следующий «прохожий» — приём «helping»: даже неудачник CAS'а на шаге 4 помогает очереди, подталкивая `tail`; неудача продвижения не ошибка).
6. Снять hazard-публикацию, разбудить спящего (если есть — протокол D7, вызывается пулом поверх push).

#### `pop` (только владелец-воркер)

1. Защитить `head` через hazard-слот (перечитать после публикации).
2. `t = tail.load(acquire)`, `next = head->next.load(acquire)`.
3. Если `head == tail`: очередь может быть пуста, но `tail` мог отстать (producer завершил шаг 4, не завершив 5) — если и `next == nullptr`, вернуть «пусто»; иначе помочь: подтолкнуть `tail` CAS'ом и повторить.
4. `next != nullptr`: прочитать задачу из `next` **до** CAS.
5. CAS `head: старый → next` (успех — задача из `next` наша; неудача — повторить с шага 1).
6. Старый фиктивный узел (бывший `head`) — в retire-список владельца (D6); снять hazard; вернуть задачу.

#### Роли и масштаб

- Производители — любые внешние потоки, их число не ограничено.
- Потребитель — воркер-владелец этого inbox (единственный; дренаж при остановках тоже выполняют воркеры — D8), поэтому CAS на `head` конкуренции почти не имеет; основная конкуренция — между производителями за `tail->next`, она же размазывается случайностью выбора воркера (D1).

### D6. Hazard pointers: домен, протокол, ретира

#### Задача

В lock-free структурах на указателях поток читает узел, который другой поток в этот момент может удалить. Hazard pointers (M. Michael, 2004) решают: «читатель объявляет узел — удаляющий обязан проверить объявления всех читателей перед освобождением».

#### Домен (по одному на процесс)

- Массив слотов: `std::atomic<void*> slots[MAX_SLOTS]`, `nullptr` = слот свободен.
- `MAX_SLOTS` фиксируется при сборке с запасом: `2 × (макс. число воркеров) + запас на внешние потоки` (порядок величины — сотни; точное значение — задача 4.1; extern-потоки приходят и уходят).
- Регистрация: `thread_local` объект-«пропуск», при первом использовании берёт свободный слот (CAS `nullptr → адрес метки`), при завершении потока (деструктор thread_local) — снимает публикацию и возвращает слот.

#### Протокол чтения (три шага, третий обязателен)

Для атомарного указателя `P`:

1. `p = P.load(acquire)` — прочитать кандидат.
2. `slot.store(p, release)` — опубликовать «я работаю с p».
3. **`P.load(acquire)` повторно**: если значение изменилось — узел уже не в структуре, наша публикация может быть неактуальна: повторить с шага 1. Если не изменилось — узел гарантированно жив всё время, пока публикация стоит.

Почему шаг 3 неустраним: между шагами 1 и 2 другой поток мог извлечь узел и удалить; без перепроверки мы объявили бы уже мёртвый адрес. Перепроверка закрывает окно: удаляющий перед освобождением сканирует слоты, а наша публикация к этому моменту либо снята, либо относится к всё ещё актуальному узлу.

В коде протокол оформляется одной функцией (`protect(...)` / `unprotect(...)`) — чтобы шаг 3 физически нельзя было пропустить (риск в конце документа).

#### Retire и скан

- Извлекший узел из структуры поток кладёт его в **свой** retire-список (обычный вектор, приватный — без синхронизации).
- Когда длина списка превышает порог **`2 × MAX_SLOTS`** (правило Майкла: при таком пороге амортизированная стоимость скана константна): собрать все публикации из всех слотов (снимки), освободить те узлы списка, которых нет ни в одном снимке; остальные остаются ждать следующего скана.
- Свойства: освобождение памяти отложено, но ограниченно (список не превосходит порога с точностью до притока); «остановки мира» нет; использование после освобождения исключено (удаляются только необъявленные).

#### Кто чем пользуется

| Структура | Что защищается слотами | Кто ретирит |
|---|---|---|
| Inbox (D5) | `tail` и `head->next` у производителей, `head`/`next` у потребителя | Потребитель — старые фиктивные узлы |
| Дека (D4) | Указатель буфера `buf` у воров на время кражи | Владелец — старые буферы после роста |

### D7. Цикл воркера, backoff и парковка

#### Скелет цикла (псевдокод уровня дизайна)

```
worker_loop:
    while (состояние == running или (draining и pending > 0)):
        задача = try_get_work()            # каскад: дека → inbox → steal
        если задача найдена:
            reset_backoff()                # следы простоя обнуляются
            выполнить задачу; --pending    # исключения уйдут в future (D9)
            продолжить
        idle_phase = advance_backoff()     # пусто → следующая фаза ожидания
        если idle_phase == SPIN:  микропауза, повторить поиск
        если idle_phase == YIELD: std::this_thread::yield(); повторить
        если idle_phase == PARK:  park()   # см. протокол ниже
    выйти из потока
```

#### Каскад `try_get_work` (порядок фиксирован спецификацией task-scheduler)

1. `deque.pop()` — свой конец.
2. `inbox.pop()`.
3. Кражи: стартовый индекс — `my_index + 1 + uniform(0, N−1)` (случайность размазывает толпу голодных воров; последовательный проход после старта бережёт кэш и предсказуем по стоимости); обходим `N−1` дек (свою пропускаем), первый успешный `steal()` — ответ.

Случайный старт — `thread_local` генератор (например, `std::minstd_rand`), засеянный `std::random_device` + номер потока; обращение к нему вне критических секций, дешёвое.

#### Три фазы backoff

| Фаза | Длительность | Что делает | Кому комфортно |
|---|---|---|---|
| SPIN | ~32 итерации | Повторяет поиск с паузой процессора (`__builtin_ia32_pause` на x86, деградация — ничего) | Всплеск работы длиной в микросекунды подхватывается мгновенно |
| YIELD | ~8 вызовов | `std::this_thread::yield()` — «ОС, отдай мой квант кому-нибудь» | Простой в миллисекунды без горения CPU |
| PARK | до сигнала | Засыпание на condvar (протокол ниже) | Долгий простой: ноль CPU, будим одного |

Числа фаз — настраиваемые константы; после любой найденной задачи счётчики фаз сбрасываются.

#### Протокол парковки без потерянных пробуждений

Общее состояние на пуле: `std::mutex park_m; std::condition_variable park_cv; std::atomic<unsigned> sleeping{0}; std::atomic<uint64_t> wake_epoch{0};`

Засыпающий воркер:

1. Финально перепроверить источники (дека, inbox) — пусто?
2. Захватить `park_m`; записать `my_epoch = wake_epoch.load(acquire)`.
3. Предикат ожидания: «эпоха сместилась ИЛИ состояние пула не running».
4. `++sleeping; park_cv.wait(lock, предикат); --sleeping;` — ожидание с предикатом само зацикливается и перечитывает условие (закрывает и ложные пробуждения condvar, и гонку «проверил — заснул»).
5. Пробудился — выйти из паркинга в общий цикл (заново полный каскад).

Пробуждающий (внешний `submit`, положивший задачу в inbox, — и только он; fork-join кладёт в деку работающего воркера, будить некого):

1. Захватить `park_m`.
2. `wake_epoch.fetch_add(1, release)` под мьютексом.
3. Если `sleeping > 0` — `park_cv.notify_one()` — **ровно один** (анти-стадо).
4. Отпустить мьютекс.

Почему потерянные пробуждения невозможны: смена эпохи и проверка предиката происходят под одним мьютексом; если пробуждающий прошёл между шагами 1 и 2 засыпающего — засыпающий увидит новую эпоху в предикате сразу и не заснёт (или мгновенно выйдет из wait). Сигнал «в море» (без держателя мьютекса) в протоколе не существует.

Кого будить — любого: разбуженный воркер делает полный каскад; если задача в чужом inbox — украдёт из деки того, кто её разберёт, или цикл повторится. Точная адресность (будить владельца inbox) — преждевременная оптимизация, отвергнута.

#### Завершение цикла

Условие выхода — в скелете: `stopped` (жёсткая остановка) или `draining && pending == 0` (мягкая: работы нет и не будет). Чтобы воркеры не проспали своё завершение, смена состояния остановки рассылает `notify_all` с новой эпохой (D8).

### D8. Остановки и деструктор

#### Машина состояний

```
                shutdown()                 shutdown_now()
   ┌──────────┐ ──────────►  ┌──────────┐ ──────────────►  ┌─────────┐
   │ RUNNING  │              │ DRAINING │                   │ STOPPED │
   └──────────┘              └──────────┘                   └─────────┘
        │                         │                              ▲
        │ ~thread_pool()          │ pending==0                   │
        └─────────────────────────┴──────────────────────────────┘
                          воркеры вышли, join, пул мёртв
```

Состояние — `std::atomic<pool_state>`; DRAINING и STOPPED — терминальные (переходов назад нет); повторные вызовы остановок — идемпотентны (no-op).

#### Graceful: счётчик `pending`

- `submit` (успешный): `pending.fetch_add(1)` до укладки задачи.
- Воркер после выполнения задачи: `pending.fetch_sub(1)`; воркер, увидевший результат 0 (он выполнил последнюю) в состоянии DRAINING, обязан разбудить всех (`park_m`; смена эпохи; `notify_all`) — иначе спящие проспят завершение.
- Выход воркера: DRAINING и `pending == 0` и свои источники пусты. `pending` глобальный, поэтому «свои пусты» — необходимая оговорка: соседние деки могут ещё содержать задачи, пока их владельцы работают; когда счётчик ноль — заведомо пусты все (каждое уменьшение происходит после выполнения, каждая укладка — до).

Замечание: steal-попытки при DRAINING продолжаются — дренаж требует, чтобы задачи не застревали в деках «никому не нужных» воркеров.

#### Immediate: слом обещаний

- `shutdown_now()`: состояние → STOPPED; воркеры выходят на ближайшей проверке цикла (текущая задача дорабатывается — прерывание на середине недопустимо: побочные эффекты, незакрытые ресурсы).
- Невыполненные задачи уничтожаются вместе с деками/inbox'ами при разрушении пула. Стандартная механика работает на нас: деструктор `std::packaged_task` (внутри `function_wrapper`), не выполнившись, разрушает promise → все связанные future получают `std::future_error` с `broken_promise` — ждущий `get()` немедленно узнаёт правду вместо вечного сна. Отдельный механизм «отмены» не нужен.

#### Деструктор

1. Если RUNNING — выполнить graceful-переход (DRAINING).
2. Дождаться выхода всех воркеров (см. выше — финальное пробуждение гарантирует, что никто не спит вечно), `join` каждого (RAII-обёртка `join_threads` из черновика владельца).
3. Теперь потоки мертвы — разрушить деки, inbox'ы, дорелизить retire-списки уже **без** hazard-сканов (конкурирующих читателей нет; слоты можно не проверять — это осознанное упрощение финализации).

### D9. `submit` и future

Пошагово:

1. `using R = std::invoke_result_t<std::decay_t<F>&>;` (тип результата вызова; `std::result_of` не используем — устарел в C++17).
2. `std::packaged_task<R()> task(std::forward<F>(f));` — адаптер, который при вызове выполнит `f` и перенаправит результат/исключение в future.
3. `auto fut = task.get_future();` — квитанция пользователю.
4. Обернуть задачу: `function_wrapper w(std::move(task));`
5. Маршрутизация:
   - Если вызывающий — воркер этого пула (определяется по `thread_local` указателю на свою деку — паттерн из черновика владельца): `pending++` (атомарно), `deque.push(std::move(w))`. Готово — будить некого (воркер сам при деле).
   - Иначе (внешний поток): проверить состояние пула; не RUNNING — бросить `std::runtime_error("submit on stopped pool")`; выбрать случайного воркера `k`; `pending++`; `inbox[k].push(std::move(w))`; выполнить протокол пробуждения (D7).
6. Вернуть `fut`.

Гарантии: исключение из `f` ловится `packaged_task` и переезжает в future (воркер лишь вызывает обёртку — падений пула нет); исключение из самого `submit` (остановленный пул) происходит **до** каких-либо изменений состояния пулов и счётчиков — транзакционно.

### D10. Бенчмарки

Методика: каждый сценарий — прогрев + 5 повторов, итог — медиана; таймер `std::chrono::steady_clock` (монотонный). Печать: таблица `пул × сценарий → задач/сек, мкс/задачу, отношение к naive`.

`naive_pool` (эталон): одна `std::deque<function_wrapper>` под `std::mutex`; воркеры ждут на `std::condition_variable`; `submit` — тот же (packaged_task + future), укладка под мьютексом; остановка — флаг + notify_all. Никакого work-stealing, никаких личных очередей — «обычный» пул, какой пишут за час.

Сценарии (по спецификации performance-benchmarks):

| Сценарий | Параметры | Что измеряет | Встроенная проверка |
|---|---|---|---|
| Миллион коротких задач | 1M задач-инкрементов атомарного счётчика, один внешний поток | Накладные расходы на задачу — худший случай | Счётчик == 1M |
| Fork-join сортировка | Массив случайных int; деление пополам через submit; порог 1000 → `std::sort` | Главный козырь work-stealing | Отсортированность + мультимножество совпадает |
| Шторм внешних submit'ов | 4 внешних потока × 250K задач | Масштабируемость пути inbox | Суммарный счётчик == 1M |

Каждый сценарий печатает строку для work-stealing и naive и отношение; README публикует результаты на машине владельца (задача 8.7).

Санитайзерная верификация (задача 8.6): CMake-опция `HPTS_SANITIZER=tsan|asan` добавляет флаги `-fsanitize=thread` / `-fsanitize=address`; прогон всех сценариев под обоими — без отчётов. Это замена автотестам на текущем этапе: гонки и ошибки памяти, не пойманные юнит-тестами, санитайзеры ловят по факту исполнения.

## Risks / Trade-offs

- **Ошибки `memory_order` — риск №1.** Дефект не воспроизводится на коротких прогонах и «стреляет» редко, под нагрузкой, на других машинах. Митигации: порядки взяты из доказанной адаптации Chase-Lev (D4), у каждой атомарной операции в коде — комментарий-обоснование (задача 3.5), CAS кражи/pop-конфликта — seq_cst без «оптимизаций»; прогоны под TSan (8.6) обязательны перед любым выводом о готовности.
- **Пропущенный шаг 3 протокола hazard** (перепроверка после публикации) — самый частый баг таких схем; в коде протокол свёрнут в одну функцию, «размазать» его по коду нельзя (D6).
- **Ретира старых буферов деки** — тонкое место D4 (вор держит буфер в момент роста): обязательный hazard-слот на `buf` в краже; сценарий «рост при активных кражах» покрыт спецификацией и прогоном под ASan.
- **Потерянные пробуждения** — закрыты протоколом эпох под одним мьютексом (D7); при ревью проверять пары «изменение эпохи ↔ notify» и предикат ожидания.
- **Пропускная способность inbox ниже деки** — осознанный размен: путь inbox — только для редких внешних задач; fork-join его не касается. Если шторм-сценарий (8.5) покажет деградацию против naive — это ожидаемо до определённого предела, зафиксировать цифры в README.
- **Измельчение fork-join**: рекурсия без порога порождает задачи дешевле накладных расходов; порог 1000 элементов в бенчмарке и рекомендация в README (D10).
- **Immediate shutdown ломает future** (`broken_promise`) — задокументированное поведение, а не дефект; альтернатива «хранить все задачи до конца» отвергнута (утечка памяти).
- **Фиксированный MAX_SLOTS** — если внешних потоков одновременно больше, чем слотов, регистрация ждёт/спинит (крайне маловероятно: сотни слотов); заложиться константой с запасом и честно задокументировать.
