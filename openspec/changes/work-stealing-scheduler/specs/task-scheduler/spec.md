## Purpose

Эта спецификация описывает публичное поведение пула потоков с work-stealing: как принимаются задачи и возвращаются результаты, как задачи порождают подзадачи (fork-join), как создаётся и останавливается пул, как ведёт себя каждый поток-воркер при поиске работы и при её отсутствии. Всё, что здесь записано, — требования к наблюдаемому поведению: они проверяются снаружи, без знания внутреннего устройства.

Термины раздела (простыми словами):
- **Воркер** — поток, принадлежащий пулу и выполняющий задачи в цикле.
- **Внешний поток** — любой поток вне пула (например, main): он только засылает задачи.
- **Дека воркера** — его личная двусторонняя очередь (устроена в capability `work-stealing-deque`).
- **Inbox воркера** — его личная входящая очередь для задач от внешних потоков (capability `lock-free-inbox`).
- **Future** — «квитанция» на результат задачи: объект `std::future<T>`, из которого позже забирается значение или исключение.

## ADDED Requirements

### Requirement: Конструирование пула
Пул создаётся либо с явно заданным числом воркеров, либо без параметра — тогда число воркеров равно `std::thread::hardware_concurrency()` (количеству логических ядер, как его видит стандартная библиотека). Каждый воркер при старте получает собственную деку и собственный inbox, которые не делятся с другими воркерами. Значение `hardware_concurrency()` не гарантировано стандартом и может вернуть 0 — в этом случае пул обязан создать хотя бы одного воркера, чтобы оставаться работоспособным.

#### Scenario: Явное число воркеров
- **WHEN** пул создаётся с параметром `thread_count = 4`
- **THEN** запускаются ровно 4 воркер-потока, каждому назначена своя дека и свой inbox

#### Scenario: Число по умолчанию
- **WHEN** пул создаётся без параметра числа потоков на машине с 8 логическими ядрами
- **THEN** создаётся 8 воркеров

#### Scenario: Деградация окружения
- **WHEN** `hardware_concurrency()` возвращает 0 (платформа не сообщила число ядер)
- **THEN** пул создаёт 1 воркера и остаётся полностью работоспособным

### Requirement: Приём задач с возвратом результата
Метод `submit(F)` принимает любой вызываемый объект `F`, вызываемый без аргументов, и возвращает `std::future<T>`, где `T` — тип выражения `F()` (для `[] { return 42; }` это `int`). Future — единственный способ получить результат: после выполнения задачи `future.get()` возвращает значение; если задача бросила исключение — `get()` перебросит это исключение вызывающему. Задачи можно засылать параллельно из любого числа внешних потоков; каждая принятая задача выполняется ровно один раз.

#### Scenario: Задача с результатом
- **WHEN** внешний поток вызывает `submit([] { return 42; })`, дожидается выполнения и вызывает `get()` у возвращённого future
- **THEN** `get()` возвращает 42

#### Scenario: Задача без результата
- **WHEN** вызывается `submit([] { /* побочный эффект */ })` для лямбды, возвращающей `void`
- **THEN** возвращается `std::future<void>`, и `get()` успешно завершается после выполнения задачи

#### Scenario: Исключение в задаче доставляется в future
- **WHEN** задача бросает исключение
- **THEN** пул продолжает принимать и выполнять другие задачи (исключение не роняет ни воркера, ни пул), а ожидающий поток получает это исключение из `future.get()`

### Requirement: Маршрутизация submit — внешний поток и воркер
Место, куда попадает задача, зависит от того, кто вызвал `submit`:

- **Вызов из внешнего потока**: задача кладётся в inbox **случайного** воркера (случайность размазывает нагрузку и не даёт всем внешним потокам упереться в одного воркера). Дальше судьбу задачи определяет владелец inbox.
- **Вызов изнутри выполняющейся задачи** (то есть воркером): задача кладётся в **собственную деку** этого воркера — мгновенно и без конкуренции с другими потоками. Это и есть fork-join: родительская задача «раздаёт» подзадачи и обычно сразу же сама их подхватывает со своего конца деки; если же появился свободный сосед — он крадёт подзадачу с другого конца.

#### Scenario: Внешний поток
- **WHEN** main-поток вызывает `submit(f)`, пока пул работает
- **THEN** задача попадает в inbox случайного воркера и в итоге выполняется ровно один раз; future задачи выполняется

#### Scenario: Fork-join — задача порождает две подзадачи
- **WHEN** выполняющаяся задача вызывает `submit(g)` и `submit(h)`, а затем дожидается `get()` обоих future
- **THEN** обе подзадачи кладутся в деку породившего воркера, выполняются ровно по одному разу (кем именно — этим же воркером или укравшими соседями — не регламентировано), родитель получает оба результата

#### Scenario: Вложенный fork-join
- **WHEN** подзадача в свою очередь порождает подзадачи
- **THEN** поведение то же: новые задачи кладутся в деку текущего воркера, все выполняются ровно по одному разу

### Requirement: Порядок поиска работы воркером
Воркер, завершив задачу, ищет следующую в строгом порядке приоритетов:

1. **Собственная дека** (pop со «своего» конца — последняя положенная задача).
2. **Собственный inbox** (задачи от внешних потоков).
3. **Кража** из деки другого воркера: первый кандидат выбирается случайно, остальные обходятся по кругу от него; собственная дека в обход не входит; полный круг безуспешен — считается «работы нет».

Порядок закреплён требованием: локальные задачи всегда приоритетнее чужих (кража — самая дорогая операция из трёх).

#### Scenario: Приоритет своей деки
- **WHEN** дека воркера содержит задачи и его inbox тоже содержит задачи
- **THEN** воркер берёт задачу из своей деки, не трогая inbox

#### Scenario: Каскад при пустой деке
- **WHEN** дека воркера пуста, а его inbox содержит задачу
- **THEN** воркер выполняет задачу из inbox, не приступая к кражам

#### Scenario: Кража при пустых деке и inbox
- **WHEN** дека и inbox воркера пусты, а дека другого воркера содержит задачи
- **THEN** воркер крадёт задачу со «старого» конца деки жертвы (самую первую положенную из находящихся там) и выполняет её

#### Scenario: Всем пусто
- **WHEN** все деки и все inbox'ы пула пусты
- **THEN** воркер не находит задачу за полный круг краж и переходит к ожиданию (см. следующее требование)

### Requirement: Трёхфазное ожидание при отсутствии работы
Если работа не найдена, воркер не крутится вечно и не засыпает сразу — он проходит три фазы:

1. **Spin (кручение)**: короткая серия повторных попыток найти работу с микропаузами. Реакция на появление задачи — практически мгновенная; расплата — процессор занят бесполезной работой, поэтому фаза короткая.
2. **Yield (уступление)**: серия вызовов `std::this_thread::yield()` — поток сообщает операционной системе «мне сейчас не горит, дай процессор другим». Нагрузка на процессор падает, задержка реакции растёт.
3. **Park (парковка)**: поток засыпает на условной переменной — полностью снимается с процессора. Нагрузка нулевая; пробуждение — самое медленное, поэтому к паркингу прибегают только после безуспешных первых двух фаз.

Правила корректности пробуждения:

- При появлении работы пул будит **не более одного** спящего воркера (будить всех — «эффект стада»: большинство проснётся, не найдёт работы и заснёт обратно, потратив процессорное время).
- **Потерянные пробуждения запрещены**: если работа появилась в промежутке между проверкой источников воркером и его засыпанием, воркер обязан обнаружить работу — либо не засыпая, либо немедленно проснувшись. Ситуация «задача лежит, все спят, пул завис» исключена конструкцией (протокол — design.md, D7).

#### Scenario: Парковка и пробуждение
- **WHEN** воркер припаркован (фаза 3), а внешний поток кладёт задачу в его inbox
- **THEN** припаркованный воркер пробуждается и выполняет задачу

#### Scenario: Будим одного, а не всех
- **WHEN** припаркованы 3 воркера и появляется одна задача
- **THEN** пробуждается не более одного воркера; остальные продолжают спать

#### Scenario: Нет ложного засыпания при гонке
- **WHEN** задача кладётся в inbox в момент, когда владелец inbox уже проверил все источники, но ещё не заснул
- **THEN** воркер обнаруживает задачу (в предикате ожидания или при повторной проверке) и выполняет её; «вечный сон при лежащей работе» не возникает

### Requirement: Мягкая остановка (graceful shutdown)
После вызова мягкой остановки:

1. Новые `submit()` отклоняются с исключением (поведение регламентировано отдельным требованием «Submit после остановки»).
2. Все задачи, **уже принятые** к этому моменту (лежащие в деках и inbox'ах, а также выполняющиеся прямо сейчас), выполняются до конца.
3. Воркеры завершаются только когда работы больше нет; после их завершения все выданные future находятся в выполненном состоянии (ни одно не остаётся «вечным обещанием»).

Мягкая остановка вызывается методом `shutdown()` и неявно — деструктором пула.

#### Scenario: Дренаж очередей
- **WHEN** в деках и inbox'ах суммарно лежат N задач и вызывается `shutdown()`
- **THEN** все N задач выполняются ровно по одному разу, все их future выполняются, после чего все потоки пула завершаются

#### Scenario: Остановка при активном fork-join
- **WHEN** вызывается `shutdown()`, пока идёт рекурсивная волна подзадач, порождающих новые подзадачи
- **THEN** уже порождённые подзадачи дорабатывают; пул завершает работу не раньше, чем выполнится последняя из них

### Requirement: Жёсткая остановка (immediate shutdown)
После вызова жёсткой остановки (`shutdown_now()`):

1. Воркеры прекращают брать новые задачи (в том числе прерывают поиск краж) и завершаются как можно скорее — дорабатывается максимум текущая выполняющаяся задача.
2. Невыполненные задачи **не выполняются** и уничтожаются вместе с очередями.
3. Future уничтоженных задач обязаны переходить в состояние ошибки (стандартный механизм: разрушение невыполненного `packaged_task` «ломает обещание» — ожидающий `get()` получает `std::future_error` c `broken_promise`), чтобы ожидающие потоки не зависали навсегда.

#### Scenario: Недоделанные задачи
- **WHEN** в очередях лежат задачи и вызывается `shutdown_now()`
- **THEN** потоки завершаются быстро; невыполнившиеся задачи не запускаются; `future.get()` каждой из них бросает `std::future_error`, а не блокируется навсегда

#### Scenario: Жёсткая остановка не роняет ожидающих
- **WHEN** поток заблокирован в `future.get()` задачи, которая уничтожена жёсткой остановкой
- **THEN** `get()` завершается с ошибкой `broken_promise`, поток продолжает жить

### Requirement: Поведение деструктора
Деструктор пула всегда приводит систему в полностью завершённое состояние: если пул ещё работал — выполняется мягкая остановка (принятые задачи дорабатывают), затем все потоки присоединяются (`join` — деструктор ждёт их фактического выхода). После возврата из деструктора: ни одного живого потока пула, ни одной «подвисшей» задачи, ни одного неразрешённого future из принятых задач. Деструктор не зависит от того, вызывал ли пользователь `shutdown()`/`shutdown_now()` явно.

#### Scenario: Разрушение работающего пула с задачами
- **WHEN** пул с невыполненными задачами разрушается без явного вызова остановки
- **THEN** задачи дорабатывают (мягкая остановка), потоки присоединяются, деструктор завершается — без зависаний и без оставшихся потоков

#### Scenario: Разрушение уже остановленного пула
- **WHEN** пользователь явно вызвал `shutdown()` (или `shutdown_now()`), дождался завершения и разрушает пул
- **THEN** деструктор завершается быстро, не выполняя работу повторно и не зависая

### Requirement: Submit после остановки
Вызов `submit()` после начала любой остановки (`shutdown()` или `shutdown_now()`) — ошибка: бросается исключение (тип — деталь реализации, зафиксированная в design.md, D9; гарантируется сам факт бросания), задача не выполняется и не попадает в очереди.

#### Scenario: Submit после мягкой остановки
- **WHEN** начата мягкая остановка и поток вызывает `submit(f)`
- **THEN** бросается исключение, задача не выполняется, future с ней не выдаётся

#### Scenario: Submit после жёсткой остановки
- **WHEN** выполнена жёсткая остановка и поток вызывает `submit(f)`
- **THEN** бросается исключение, задача не выполняется
