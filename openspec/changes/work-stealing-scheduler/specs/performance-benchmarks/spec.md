## Purpose

Замеры производительности — доказательная часть проекта: цифры, подтверждающие (или опровергающие — тоже полезный результат) преимущество work-stealing пула над классическим пулом с одной общей очередью на мьютексе. Спецификация фиксирует: пул-эталон для сравнения, сценарии нагрузки, измеряемые метрики, методику прогона и способ запуска — всё через CMake, без внешних тестовых фреймворков (решение владельца).

Термины раздела:
- **Базовая линия (baseline, эталон)** — наивный пул с той же функциональностью, но простейшей реализацией; с ней сравнивают основной пул.
- **Throughput (пропускная способность)** — сколько задач в секунду обрабатывает пул.
- **Время на задачу** — величина, обратная throughput: сколько микросекунд в среднем уходит на одну задачу (включая накладные расходы пула).
- **Медиана прогонов** — центральное значение из нескольких повторов измерения; устойчивее к случайным всплескам системы, чем среднее.

## ADDED Requirements

### Requirement: Базовая линия для сравнения
В состав бенчмарков входит наивный пул (`naive_pool`): одна общая очередь задач (`std::deque`) под `std::mutex` («замком»: поток захватывает замок, работает с очередью, отпускает), условная переменная для пробуждения ожидающих потоков, то же число воркеров и тот же внешний API `submit(F) → std::future<T>`. Ни work-stealing, ни личных очередей. Назначение — честная точка отсчёта: оба пула проходят одинаковые сценарии в одинаковых условиях на одной машине.

#### Scenario: Одинаковые условия сравнения
- **WHEN** запускается любой сценарий замера
- **THEN** оба пула (work-stealing и naive) выполняют один и тот же набор задач с одним и тем же числом потоков на одной машине в рамках одного запуска бенчмарка

#### Scenario: Эквивалентная функциональность эталона
- **WHEN** naive_pool используется в сценариях с future и fork-join
- **THEN** он возвращает корректные результаты через `submit → future` (эталон обязан быть правильным, пусть и медленным)

### Requirement: Сценарий «миллион коротких задач»
Назначение: измерить накладные расходы пула на «дешёвых» задачах — худший случай для любого планировщика, где стоимость управления задачей сравнима со стоимостью самой задачи. Нагрузка: 1 000 000 независимых тривиальных задач (например, инкремент атомарного счётчика), засылаемых внешним потоком. Метрики: задач в секунду (throughput) и среднее время на задачу.

#### Scenario: Прогон сценария
- **WHEN** сценарий выполняется для обоих пулов
- **THEN** печатается throughput (задач/сек) и время на задачу для каждого пула, а также отношение (во сколько раз work-stealing быстрее или медленнее naive)

#### Scenario: Корректность счётчика
- **WHEN** все 1 000 000 задач выполнены
- **THEN** итоговое значение счётчика равно 1 000 000 — каждая задача выполнена ровно один раз

### Requirement: Сценарий «fork-join рекурсивная сортировка»
Назначение: измерить главный козырь work-stealing — рекурсивное деление работы. Нагрузка: сортировка большого массива, где задача делит массив на две половины, порождает две подзадачи через `submit` и объединяет результаты после их выполнения; ниже порога (~1000 элементов) подзадача сортирует последовательно (`std::sort`) — защита от измельчения задач до размера меньшего накладных расходов. Метрика: общее время сортировки; корректность обязательна: результат проверяется на отсортированность.

#### Scenario: Корректность и скорость
- **WHEN** массив из N случайных элементов сортируется обоими пулами
- **THEN** оба результата проверены на отсортированность (и совпадение мультимножества элементов с исходным массивом), напечатано время каждого пула и их отношение

#### Scenario: Порог мелкости задач
- **WHEN** подмассив становится меньше порога
- **THEN** подзадача сортирует его последовательно, не порождая новых подзадач (чтобы цена порождения не превышала работу)

### Requirement: Сценарий «шторм внешних submit'ов»
Назначение: нагрузить путь внешнего приёма задач (inbox случайного воркера — у naive: общая очередь под мьютексом) и проверить его масштабируемость при конкуренции засылающих потоков. Нагрузка: 4 внешних потока одновременно засылают по 250 000 задач каждый (итого 1 000 000).

#### Scenario: Параллельный засыл
- **WHEN** 4 внешних потока одновременно засылают по 250 000 задач каждый, обе стороны дожидаются выполнения
- **THEN** все 1 000 000 задач выполнены ровно один раз (проверка счётчиком), напечатан throughput обоих пулов и отношение

### Requirement: Методика и запуск через CMake
Измерения воспроизводимы: каждый сценарий выполняется несколько повторов (например, 5), фиксируется медиана (устойчивость к случайным всплескам системы); перед замерами — прогревочный прогон. Время измеряется собственным таймером на `std::chrono::steady_clock` (монотонные часы, не подвержены переводам системного времени). Все бенчмарки собираются и запускаются целями CMake; результаты печатаются в человекочитаемом виде (таблица: пул, сценарий, задач/сек, мкс/задачу, отношение к эталону).

#### Scenario: Сборка и запуск
- **WHEN** выполняется цель бенчмарка из CMake (`cmake --build build --target bench && ./build/bench`)
- **THEN** все сценарии прогоняются автоматически и печатают таблицу метрик без ручных действий

#### Scenario: Повторы и медиана
- **WHEN** сценарий выполняется
- **THEN** итоговая метрика — медиана по всем повторам прогона, а не единичное измерение
