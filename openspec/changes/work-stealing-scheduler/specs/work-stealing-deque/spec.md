## Purpose

Дека Chase-Lev — безблокировочная (lock-free: без мьютексов; зависание одного потока не мешает прогрессу остальных) двусторонняя очередь, личная для каждого воркера. Это «горячее сердце» планировщика: операции владельца в неконкурирующем случае сводятся к записи в массив и одной атомарной операции над счётчиком, а значит fork-join раздача подзадач почти ничего не стоит. Здесь зафиксированы требования к её наблюдаемому поведению: порядок с каждого конца, разрешение одновременной борьбы за одну задачу, динамический рост и гарантии видимости записей между потоками.

Термины раздела:
- **Владелец** — единственный поток, которому принадлежит дека (воркер). Только он может класть задачи и забирать их со «своего» конца.
- **Вор** — любой другой поток, забирающий задачи с противоположного конца.
- **bottom** — конец деки владельца: сюда кладутся задачи, отсюда же забираются (порядок LIFO — «последним положил, первым забрал»).
- **top** — противоположный конец, с которого крадут воры (порядок FIFO — «первым положена, первым украдена»).
- **CAS (compare-and-swap)** — атомарная операция «если значение равно прочитанному мной — замени на новое; иначе сообщи о неудаче». Позволяет потокам конфликтовать безопасно: при неудаче операция просто повторяется.

## ADDED Requirements

### Requirement: Владельческие операции с конца bottom
Владелец выполняет две операции со своего конца: `push` — положить задачу, `pop` — забрать последнюю положенную. Совокупность даёт порядок LIFO: как стек. В отсутствие конкуренции (воров нет или они неактивны) эти операции не содержат CAS-циклов и не блокируются — стоимость близка к обычной записи в массив плюс одна атомарная запись счётчика. `pop` пустой деки — легальный случай: возвращает признак «пусто», не блокируется и не бросает исключений.

#### Scenario: Порядок LIFO у владельца
- **WHEN** владелец кладёт задачи A, B, C (в этом порядке) и затем трижды выполняет pop без конкуренции
- **THEN** задачи извлекаются в порядке C, B, A

#### Scenario: Pop пустой деки
- **WHEN** владелец выполняет pop пустой деки
- **THEN** возвращается «пусто»; никаких исключений, блокировок и ожиданий

#### Scenario: Interleave владельца
- **WHEN** владелец кладёт A, B, забирает (получает B), кладёт C, дважды забирает
- **THEN** получает C, затем A — состояние деки консистентно на каждом шаге

### Requirement: Кража с конца top
Чужой поток (вор) выполняет единственную доступную ему операцию `steal` — забрать старейшую задачу деки (с конца `top`, порядок FIFO). Логика FIFO: старейшая задача — обычно «корень» крупного куска работы, украв который вор надолго обеспечит себя занятостью и не будет беспокоить жертву вновь. `steal` пустой деки возвращает «пусто» без блокировки; `steal` никогда не кладёт задач в деку.

#### Scenario: Вор забирает старейшую задачу
- **WHEN** дека содержит задачи A, B, C (A положена раньше всех) и вор выполняет steal
- **THEN** вор получает A; следующие steal'ы получат B, затем C

#### Scenario: Steal пустой деки
- **WHEN** вор выполняет steal пустой деки
- **THEN** возвращается «пусто»; без исключений, блокировок и ожиданий

#### Scenario: Совместный разбор деки
- **WHEN** дека содержит A, B, C; владелец делает pop дважды, а вор — steal, в любом перемешанном порядке
- **THEN** суммарно извлечены ровно три задачи по одной каждым успешным действием; с конца bottom выходят последние положенные, с конца top — старейшие из оставшихся

### Requirement: Одновременная борьба за задачу разрешается единственным победителем
Задача в деке — единичный экземпляр: отдать её можно только одному претенденту. Когда за последнюю задачу деки одновременно борются несколько участников (владелец своим `pop` и/или несколько воров своими `steal`), ровно один получает задачу, остальные получают «пусто». Ни при каком чередовании операций задача не выдаётся дважды и не теряется (извлечена без выполнения владельцем — не её дело; требование про саму деку: каждый успешный pop/steal возвращает различные, не выданные ранее задачи).

#### Scenario: Два вора дерутся за последнюю задачу
- **WHEN** дека содержит одну задачу и два вора одновременно выполняют steal
- **THEN** ровно один вор получает задачу, второй получает «пусто»; декa остаётся пустой и консистентной

#### Scenario: Владелец против вора за последнюю задачу
- **WHEN** дека содержит одну задачу; владелец выполняет pop одновременно с steal'ом вора
- **THEN** задача достаётся ровно одному из двух, второй получает «пусто»

#### Scenario: Много воров, много задач
- **WHEN** дека содержит K задач и одновременно K воров (и владелец) выполняют по одному извлечению
- **THEN** количество успешных извлечений равно количеству задач, находившихся в деке; каждый победитель получил уникальную задачу

### Requirement: Динамический рост буфера
Ёмкость деки не фиксирована: когда владелец кладёт задачу в заполненный буфер, дека увеличивает ёмкость (выделяется новый массив большего размера, элементы переносятся, новый буфер становится видимым ворам). Рост — привилегия только владельца; воры в любой момент видят непротиворечивое состояние: рост не приводит к потере задач, их дублированию, выдаче «мусорных» задач или доступу к уже освобождённой памяти. После роста все ранее положенные задачи остаются доступны для извлечения.

#### Scenario: Переполнение и рост
- **WHEN** владелец кладёт больше задач подряд, чем текущая ёмкость буфера
- **THEN** буфер незаметно растёт; все задачи доступны владельцу в LIFO-порядке, как если бы роста не было

#### Scenario: Рост при активных кражах
- **WHEN** владелец переполняет буфер и вызывает рост, пока воры выполняют steal из этой деки
- **THEN** каждый steal либо возвращает корректную задачу, либо «пусто»; ни потерь, ни дубликатов, ни обращений к освобождённой памяти

### Requirement: Гарантии видимости памяти
Дека — структура без мьютексов; согласование потоков выполняется атомарными операциями с явно указанными порядками памяти (`memory_order`). Ключевая гарантия: если владелец положил задачу, а вор успешно украл её слот, вор обязан увидеть полностью записанную (инициализированную) задачу — «полузаписанных» задач не существует. Аналогично при росте: вор, начавший кражу после публикации нового буфера, видит согласованные счётчики и данные.

#### Scenario: Опубликованная задача видна вору
- **WHEN** владелец кладёт задачу, и вор немедленно успешно выполняет steal этого слота
- **THEN** вор наблюдает задачу целиком: именно тот объект, который положил владелец, без «мусорных» полей

#### Scenario: Горячий путь без мьютексов
- **WHEN** выполняются любые операции деки при любой конкуренции
- **THEN** ни одна из них не захватывает мьютекс (инструментальная проверка — в бенчмарк-верификации задач 8.6: прогон под детектором гонок не находит гонок на пути деки)
