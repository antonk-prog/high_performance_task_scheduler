## Purpose

Inbox — входящая безблокировочная очередь каждого воркера, единственная точка входа задач от внешних потоков (в личную деку Chase-Lev класть может только хозяин — см. capability `work-stealing-deque`, а глобальной очереди на мьютексе в проекте сознательно нет). Реализуется классическим алгоритмом Майкла-Скотта: очередь на односвязном списке с атомарными операциями CAS, пригодная для многих производителей (внешних потоков) и потребителя (воркер-владелец). Освобождение памяти удалённых из очереди узлов — через hazard pointers: схему, при которой поток перед работой с узлом публично «объявляет» его, а узлы освобождаются только если их никто не объявил.

Термины раздела:
- **Производитель** — внешний поток, вызывающий `push` (кладёт задачу).
- **Потребитель** — воркер-владелец inbox, вызывающий `pop` (забирает задачу).
- **Узел** — элемент связного списка: содержит задачу и указатель на следующий узел.
- **Фиктивный (dummy) узел** — всегда присутствующий «пустышка» в голове очереди; благодаря ему `pop` никогда не работает с нулевыми указателями, а данные читаются из узла, следующего за головой.
- **Hazard pointer** — ячейка, в которой поток публикует адрес узла, который собирается читать; пока адрес опубликован, узел гарантированно не освобождён.
- **Retire («выход на пенсию»)** — отложенное удаление: извлечённый из очереди узел не освобождается немедленно, а ждёт проверки «не держит ли его кто-нибудь».

## ADDED Requirements

### Requirement: Многопоточное помещение и извлечение
Inbox — очередь MPMC (много производителей, минимум один потребитель): `push` может одновременно вызываться из любого числа внешних потоков; `pop` выполняет владелец-воркер. Извлечение — в порядке FIFO: задачи выходят в том порядке, в котором были успешно положены. Все операции безблокировочные (lock-free): при любой конкуренции хотя бы один поток гарантированно продвигается; зависание или задержка любого потока не блокирует навсегда продвижение остальных.

#### Scenario: Параллельные производители
- **WHEN** K внешних потоков одновременно кладут по N задач в один inbox, после чего владелец извлекает задачи до опустошения
- **THEN** извлечено ровно K×N задач, каждая ровно один раз (дублирования и потери исключены)

#### Scenario: FIFO порядок при одном производителе
- **WHEN** один поток кладёт задачи A, B, C (без конкуренции), затем владелец трижды извлекает
- **THEN** задачи извлечены в порядке A, B, C

#### Scenario: Извлечение на фоне активного засыла
- **WHEN** производители продолжают класть задачи, пока владелец извлекает
- **THEN** каждая задача извлекается ровно один раз; порядок между задачами одного производителя соответствует FIFO (между разными производителями порядок не регламентирован)

### Requirement: Фиктивный головной узел
Очередь реализована по схеме Майкла-Скотта с фиктивным узлом: голова (`head`) всегда указывает на реально существующий узел-«пустышку», данные же читаются из следующего за ним узла. Инвариант исключает разыменование нулевых указателей в `pop`; «пустая очередь» — это очередь из одного фиктивного узла (`head == tail`).

#### Scenario: Извлечение из пустой очереди
- **WHEN** владелец вызывает pop пустого inbox (в нём только фиктивный узел)
- **THEN** возвращается «пусто»: без блокировок, исключений и разыменования нулевых указателей; очередь остаётся консистентной для последующих push/pop

#### Scenario: Push в пустую очередь
- **WHEN** производитель кладёт задачу в пустой inbox
- **THEN** следующий pop владельца успешно возвращает именно эту задачу

### Requirement: Освобождение памяти через hazard pointers
Проблема, которую решает требование: производитель читает `tail` и `tail->next`, а потребитель в этот же момент может извлечь узел и освободить его — получается обращение к освобождённой памяти (use-after-free). Протокол hazard pointers закрывает её:

1. Прежде чем работать с указателем, поток публикует его адрес в собственном hazard-слоте (одном на поток).
2. После публикации поток **обязан перечитать** исходный атомарный указатель: если тот изменился — узел уже не актуален, попытка повторяется; если не изменился — узел гарантированно жив, пока публикация не снята.
3. Извлечённый из очереди узел отправляется в retire-список потока-извлекателя.
4. Периодически (когда retire-список превышает порог) поток сканирует все hazard-слоты и освобождает те узлы списка, чьего адреса нет ни в одном слоте.

Гарантии: ни один узел не освобождается, пока его адрес опубликован хотя бы одним потоком; память в конечном итоге освобождается — объём «висящей» в retire-списках памяти ограничен порогом, остановка мира (глобальная пауза всех потоков) не требуется.

#### Scenario: Защита удерживаемого узла
- **WHEN** поток A опубликовал адрес узла N в своём hazard-слоте и читает его, а поток B извлёк N из очереди и провёл скан своих retire-списков
- **THEN** B обнаруживает N в hazard-слоте A и не освобождает N; узел будет освобождён одним из последующих сканов, после того как A снимет публикацию

#### Scenario: Узел в итоге освобождается
- **WHEN** узел извлечён из очереди, его адреса нет ни в одном hazard-слоте, а его владелец-ретирер проводит очередной скан
- **THEN** память узла освобождается при этом скане (не накапливается бесконечно и не требует остановки программы)

#### Scenario: Перепроверка после публикации
- **WHEN** поток публикует адрес узла в слоте, но исходный указатель очереди успел измениться до перепроверки
- **THEN** поток обнаруживает расхождение на шаге перепроверки и повторяет попытку с актуальным узлом; работа с «устаревшим» узлом не выполняется

### Requirement: Отсутствие потерь и дублирования
Инвариант целостности при любой конкуренции и любом чередовании операций: количество успешных извлечений за время жизни очереди равно количеству успешных помещений (после её опустошения); каждая задача выдаётся потребителю ровно один раз; ни один поток никогда не обращается к освобождённой памяти.

#### Scenario: Шторм производителей и потребителя
- **WHEN** множество внешних потоков непрерывно кладёт задачи, а владелец непрерывно извлекает, до общего «покоя» (производители закончили, очередь опустошена)
- **THEN** сумма успешных извлечений равна сумме успешных помещений; ни одна операция не вернула повреждённую или «мусорную» задачу

#### Scenario: Прохождение санитайзера
- **WHEN** шторм-сценарий выполняется под детектором гонок и детектором ошибок памяти (ThreadSanitizer/AddressSanitizer, задача 8.6)
- **THEN** инструменты не сообщают об ошибках: ни гонок, ни use-after-free, ни утечек
