## 3. Chase-Lev дека (D4)

- [ ] 3.1 **Каркас деки**
  - Что: `src/work_stealing_deque.hpp/.cpp`: класс с `std::atomic<int64_t> top, bottom`, `std::atomic<Buffer*> buf`; структура `Buffer` (массив `function_wrapper`, ёмкость — степень двойки, начальная 1024); индексация `i & (ёмкость−1)`; конструктор пустой деки.
  - Проверка: компиляция; единственный поток: push/pop пустой деки возвращает «пусто».
- [ ] 3.2 **Операции владельца: push и pop**
  - Что: `push` по протоколу D4 (шаги 1–4: relaxed-запись слота, затем `bottom` store **release**); `pop` (acquire `bottom`, декремент; обычный случай — без CAS; крайний случай `b == t` — CAS `top` **seq_cst**, неудача = «пусто»; случай `b < t` — «пусто» с выравниванием `bottom`). Порядки и их обоснование — комментариями у каждой строки (по образцу D4).
  - Проверка: временный однопоточный тест в `bench.cpp`: push A, B, C → pop даёт C, B, A; pop пустой — «пусто» без исключений.
- [ ] 3.3 **Кража steal**
  - Что: `steal` по протоколу D4 (acquire `top`; проверка пустоты; чтение задачи из слота **до** CAS; CAS `top → top+1` **seq_cst**; «пусто» при неудаче). Без hazard-защиты буфера — она добавляется в 3.4 (пока роста нет, буфер не меняется — безопасно).
  - Проверка: временный двухпоточный тест: поток 1 (владелец) кладёт 1000 задач, поток 2 крадёт в цикле до «пусто»; суммарно pop'ы владельца + steal'ы вора == 1000, ни потерь, ни дубликатов (счётчик).
- [ ] 3.4 **Рост буфера при переполнении** (зависит от 4.1 — сначала сделать hazard-домен)
  - Что: в `push` при `bottom − top == ёмкость`: выделить буфер ×2, перенести задачи из `[top, bottom)`, `buf.store(новый, release)`; старый буфер — в retire-список владельца (через домен 4.1). В `steal` — публикация указателя `buf` в hazard-слоте на время операции (шаг 3 протокола D4) и снятие после.
  - Проверка: тест роста: положить 5000 задач (ёмкость 1024 → рост несколько раз) при активном воре — инвариант «pop'ы + steal'ы == 5000» сохраняется; прогон под ASan без ошибок памяти.
- [ ] 3.5 **Ревью порядков памяти** (спека work-stealing-deque, требование «Гарантии видимости памяти»)
  - Что: построчная сверка всех `load/store/CAS` деки с D4: у каждой операции — комментарий, почему именно этот порядок (relaxed/acquire/release/seq_cst); отдельное внимание: seq_cst в крайнем случае pop и в steal (не ослаблять!).
  - Проверка: таблица в комментарии заголовка файла «операция → порядок → почему» полна (нет операций без обоснования); двухпоточный стресс (3.3–3.4) под TSan — чисто.

## 4. Hazard pointers (D6)

- [ ] 4.1 **Домен hazard-слотов**
  - Что: `src/hazard_pointers.hpp/.cpp`: массив `std::atomic<void*> slots[MAX_SLOTS]` (константа с запасом, например `2×64+128`); `thread_local` регистрация потока (взятие свободного слота CAS'ом при первом использовании, освобождение в деструкторе thread_local); функции-протокол: `protect(источник) -> указатель` (три шага: прочитать → опубликовать → **перечитать и проверить**; при расхождении — повтор) и `unprotect()`; `retire(узел)` — в приватный список потока; `scan()` — при превышении порога `2×MAX_SLOTS`: снимки всех слотов, освобождение необъявленных.
  - Проверка: временный тест: два потока, один публикует и «задумывается» (sleep), второй ретирит и сканирует — узел под публикацией не освобождён; после снятия публикации и следующего скана — освобождён (наблюдение через счётчик живых узлов).

## 5. Inbox: очередь Майкла-Скотта (D5)

- [ ] 5.1 **Очередь с hazard-защитой**

## 6. Цикл воркера (D7)

- [ ] 6.1 **Каскад поиска работы**
  - Что: `src/worker.hpp/.cpp`: `try_get_work(воркер)` — последовательно: `deque.pop()` → `inbox.pop()` → обход краж: старт `my_index + 1 + uniform(0, N−1)` (thread_local PRNG на `random_device`), затем по кругу `N−1` чужих дек, первый успешный steal. Себя в обход не включать.
  - Проверка: временный запуск с логированием индексов краж (только для проверки): старты распределены по разным индексам, своя дека никогда не является жертвой.
- [ ] 6.2 **Трёхфазный backoff и парковка**
  - Что: счётчик фаз idle (сброс при найденной задаче); фазы по D7: SPIN ~32 итераций (с паузой процессора — `#if defined(__x86_64__)` → `_mm_pause`, иначе ничего), YIELD ~8 вызовов, PARK — протокол засыпания: перепроверка источников → захват `park_m` → чтение `my_epoch` → `++sleeping` → `wait(lock, предикат «эпоха сменилась или состояние ≠ running»)` → `--sleeping`. Общее состояние (`park_m`, `park_cv`, `sleeping`, `wake_epoch`) — на пуле.
  - Проверка: ручной сценарий: пул без задач + парковка всех воркеров (наблюдение: загрузка CPU падает до нуля); появление одной задачи будит ровно одного (лог пробуждений).
- [ ] 6.3 **Пробуждение при появлении внешней работы**
  - Что: функция `wake_one_if_sleeping()`: захват `park_m`; `wake_epoch.fetch_add(1, release)`; при `sleeping > 0` — `notify_one()`. Вызывается из внешнего пути `submit` (D9) после укладки задачи в inbox.
  - Проверка: сценарий гонки из спеки task-scheduler («нет ложного засыпания»): воркер на пороге паркинга, submit в этот момент — задача выполняется без длительного сна (проверка таймингом: результат до контрольного сна).

## 7. Фасад thread_pool (D8, D9)

- [ ] 7.1 **Конструктор и старт воркеров**
  - Что: `include/hpts/thread_pool.hpp` + `src/thread_pool.cpp`: конструктор `explicit thread_pool(unsigned thread_count = default)`, default = `hardware_concurrency()`, при 0 → 1; на каждый воркер: дека, inbox, объект воркера; `thread_local` привязка воркера к своим структурам (паттерн черновика владельца); RAII `join_threads` (join всех в деструкторе члена).
  - Проверка: пул на 4 воркера создаётся и разрушается (пустой) без зависаний; число потоков в системе во время работы == 4 (наблюдение отладчиком/логом).
- [ ] 7.2 **submit с future и маршрутизация**
  - Что: `submit(F)` по D9: `invoke_result_t`; `packaged_task`; future наружу; маршрутизация воркер/внешний; случайный выбор inbox; `pending++` до укладки; внешний путь вызывает `wake_one_if_sleeping()`.
  - Проверка: `submit([]{ return 42; })` → `get() == 42`; задача с `throw` → исключение в `get()`, пул жив (следующая задача выполняется); fork-join из задачи: две подзадачи + оба `get()` (врем. код).
- [ ] 7.3 **Graceful shutdown**
  - Что: `shutdown()`: переход RUNNING → DRAINING (CAS, идемпотентность); `pending`-счётчик (инкремент в submit до укладки, декремент после выполнения); выход воркера при `DRAINING && pending == 0`; воркер, обнуливший pending, — финальное пробуждение всех (смена эпохи + `notify_all`).
  - Проверка: заслать 100K задач, тут же `shutdown()`, дожидаться деструктора — счётчик выполненных == 100K; все future выполнены; время завершения конечно (нет «вечно спящих» — финальный notify_all).
- [ ] 7.4 **Immediate shutdown**
  - Что: `shutdown_now()`: переход → STOPPED; воркеры выходят на ближайшей проверке цикла; при разрушении структур невыполненные задачи уничтожаются — их future получают `broken_promise` (механика `packaged_task`, отдельный код не нужен — проверить, что задачи реально доживают до разрушения пула в невыполненном виде).
  - Проверка: заслать медленные задачи (sleep), `shutdown_now()` — потоки завершаются быстро; `get()` невыполненной задачи бросает `std::future_error`, ожидающий поток не зависает.
- [ ] 7.5 **Деструктор и submit после остановки**
  - Что: деструктор = graceful-переход (если RUNNING) + join + финализация (retire-списки освобождаются без сканов — потоки мертвы); `submit` при состоянии ≠ RUNNING бросает `std::runtime_error` до любых изменений состояния.
  - Проверка: прогон всех сценариев спеки task-scheduler вручную (врем. код): разрушение занятого пула; разрушение уже остановленного; submit после обеих остановок — исключения.
