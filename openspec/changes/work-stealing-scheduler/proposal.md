## Why

### Что за система и зачем она нужна

Планировщик задач (task scheduler) — это механизм, который принимает кусочки работы («задачи») от программы и распределяет их по потокам выполнения. Простейший вариант — пул потоков с одной общей очередью: потоки стоят у очереди и разбирают задачи по мере поступления. Проблема общей очереди: когда потоков много, они толкаются у одного «окна выдачи» — каждый захват очереди сопровождается ожиданием и обменом данными между ядрами процессора.

Work-stealing («воровство работы») решает это разделением: **каждый поток получает собственную очередь задач**. Тогда конфликтов за одну очередь почти нет, а балансировка достигается иначе — поток, у которого очередь опустела, не сидит без дела, а «крадёт» задачи из очередей соседей.

Ключевая асимметрия (почему это быстро):

- **Свои** задачи поток берёт с того конца очереди, куда их кладёт (последняя положенная — «горячая»: её данные с наибольшей вероятностью ещё находятся в кэше процессора — сверхбыстрой памяти рядом с ядром). Порядок получается «последним пришёл — первым ушёл» (LIFO).
- **Чужие** задачи вор забирает с противоположного конца — самые старые. Старая задача — обычно «корень» большого куска работы: украв её, вор надолго обеспечивает себя работой и не будет беспокоить соседа снова. Порядок «первым пришёл — первым ушёл» (FIFO).

Для такой двусторонней очереди существует специальный безблокировочный алгоритм — дека Chase-Lev (подробно — в design.md, решение D4).

## What Changes

Создаётся библиотека на C++17. Состав по компонентам:

### 1. Chase-Lev work-stealing дека (ядро)

Безблокировочная двусторонняя очередь на кольцевом буфере (массив, индексы в котором «заворачиваются» по кругу: за последним элементом следует первый). Владелец кладёт и забирает задачи со своего конца практически без синхронизации с другими потоками — это «горячий путь», ради которого всё затевается. Чужие потоки-воры забирают задачи с другого конца через атомарную операцию сравнения-и-обмена (CAS — compare-and-swap: «замени значение, если оно всё ещё равно тому, что я прочитал»; если нет — операция неудачна и повторяется). Переполнение буфера решается ростом: выделяется массив вдвое больше, элементы переносятся.

### 2. Lock-free inbox — входящая очередь каждого воркера

Кольцевая дека Chase-Lev имеет жёсткое ограничение: **класть в неё может только поток-хозяин**. Но задачи в пул засылают и внешние потоки (например, main). Для них у каждого воркера предусмотрен отдельный «входящий ящик» (inbox) — безблокировочная очередь Майкла-Скотта (классический алгоритм очереди на связном списке, пригодный для многих потоков-производителей). Внешний `submit()` выбирает **случайного** воркера и кладёт задачу в его inbox (решение владельца); владелец inbox'а забирает задачи оттуда в свободное время.

Освобождение памяти узлов очереди — через **hazard pointers** («указатели-опасности», схема Майкла): поток, прежде чем работать с узлом списка, публично объявляет «я держу этот узел» в специальной ячейке; удаляющий поток проверяет эти ячейки и не освобождает объявленные узлы. Выбор владельца — вместо более простой схемы отложенного удаления (причины — в design.md, D6).

### 3. Цикл воркера и ожидание работы

Каждый поток-воркер работает по циклу: (1) забрать из своей деки; (2) забрать из своего inbox; (3) украсть из деки случайного соседа (старт случайный, дальше обход по кругу); (4) если всюду пусто — стратегия ожидания из трёх фаз: короткое активное «кручение» (spin — мгновенная реакция на появление работы, ценой пустого расхода процессора), затем уступание кванта операционной системе (yield), затем засыпание на условной переменной (park — ноль нагрузки на процессор, но пробуждение медленнее). При появлении работы пул будит **ровно одного** спящего — чтобы не поднимать всех попусту («эффект стада»).

### 4. Публичный API пула

- `submit(F)` — принимает любой вызываемый объект, возвращает `std::future<T>` — «квитанцию», по которой позже забирается результат. Реализация: лямбда упаковывается в `std::packaged_task` (стандартный адаптер, переносящий результат или исключение в future), а сам объект задачи — в собственную обёртку `function_wrapper` (type erasure — стирание типа: храним объект через указатель на базовый класс с виртуальным вызовом; нужно потому, что `std::function` требует копируемости, а `packaged_task` копировать нельзя).
- **Fork-join** — задачи могут порождать подзадачи: задача, выполняющаяся воркером, вызывает `submit()` — задача кладётся в деку этого же воркера мгновенно и без конкуренции; родитель дожидается результатов детей через их future.
- Конструктор: число потоков задаётся, по умолчанию — число логических ядер (`hardware_concurrency`).
- Остановка в двух режимах: **graceful** (мягкая — новых задач не принимаем, все принятые доделываем) и **immediate** (жёсткая — останавливаемся сразу; невыполенные задачи уничтожаются, их future сообщают об ошибке, чтобы ждущие не зависали навсегда). Деструктор всегда выполняет мягкую остановку и присоединяет потоки.
- Исключение, брошенное задачей, не роняет пул — оно доставляется вызвавшему через future.

### 5. Замеры производительности

Чтобы «high-performance» в названии было подкреплено цифрами: три сценария (миллион коротких задач; fork-join рекурсивная сортировка; параллельный засыл задач из четырёх внешних потоков) прогоняются для нашего пула и для **наивного пула-эталона** (одна общая очередь на мьютексе — «замке», который потоки захватывают по очереди). Метрики: задач в секунду и время на задачу; печать сравнительной таблицы. Свои таймеры на `std::chrono`, без внешних фреймворков.

## Capabilities

### New Capabilities

- `task-scheduler`: пул потоков и публичный API — правила приёма задач и возврата результатов, fork-join, конструирование, оба режима остановки, поведение деструктора, доставка исключений, цикл воркера и трёхфазное ожидание.
- `work-stealing-deque`: дека Chase-Lev — операции владельца (LIFO) и воров (FIFO), разрешение одновременной борьбы за одну задачу, динамический рост буфера, гарантии видимости записей между потоками.
- `lock-free-inbox`: inbox-очередь Майкла-Скотта — много производителей/один потребитель, фиктивный головной узел, освобождение памяти через hazard pointers, отсутствие потерь и дублирования задач.
- `performance-benchmarks`: сценарии замеров, пул-эталон для сравнения, метрики и запуск через CMake.

## Impact

- **Новый код**: весь проект. Модули: `function_wrapper` (обёртка задач), дека Chase-Lev, очередь Майкла-Скотта, домен hazard pointers, цикл воркера с ожиданием, фасад `thread_pool`, бенчмарки с наивным пулом-эталоном. Структура файлов — в design.md (D2).
- **Зависимости**: сам пул — исключительно стандартная библиотека C++17 (`<atomic>`, `<thread>`, `<future>`, `<condition_variable>` и др.); бенчмарки — без внешних фреймворков (решение владельца).
- **Инфраструктура**: CMake; сборка с опциями санитайзеров (инструментов поиска ошибок памяти и гонок — ASan/TSan) для ручной проверки; README на русском; без CI.
- **Не входит в объём (non-goals)**: отмена выполняющихся задач; приоритеты задач; цепочки продолжений (`then`); тестовый фреймворк и автоматические тесты (отложено владельцем до будущих версий); CI; динамическое изменение числа воркеров.
- **Опорные материалы**: черновики владельца — `function_wrapper` (берём с минимальными правками), цикл воркера с каскадом поиска задач (перерабатывается), стек со схемой отложенного освобождения памяти (отклонён в пользу hazard pointers по решению владельца). Подробный разбор — в design.md, раздел «Context».
- **Риски** (подробно — в design.md): корректность порядков памяти (`memory_order`) в деке — ошибки не воспроизводятся на коротких тестах и всплывают редко, только под нагрузкой; протокол hazard pointers требует обязательной перепроверки после публикации указателя; парковка потоков чревата «потерянными пробуждениями» (задача появилась, а спящего не разбудили — пул завис) — закрыто протоколом эпох; рекурсивный fork-join без порога остановки измельчает задачи до размера меньшего, чем накладные расходы на их порождение.
